## 1. 评审结论摘要

**文档集整体质量在「个人重写工具」这一档位里属于中上**：分层清晰、模块边界合理、Task 抽象与 Client 统一出口是对的，数据库以「下载记录」为核心、留了 `schema_version` 迁移表，这些都值得保留。

**但按当前文档直接开工，会在四个地方必然翻车**（H 级），且其中两个（H1、H2）会让「增量同步」和「失败重试」这两个 P0 需求直接失效：

- **可直接采纳的设计点：14 项**（见 §3）
- **定稿前须解决（硬冲突）：6 项 H1–H6**（§4，按字面实现会出错或失控）
- **同步缺口：14 项 S1–S14**（§5，文档之间或与真实接口不一致）
- **打磨项：7 项 P1–P7**（§6）
- **待拍板取舍：5 项 Q1–Q5**（§7，属决策题不是缺陷题）

一句话：**架构不用推翻，需要补的是「配额经济学」「去重语义」「并发写库」「阶段口径」这四件事**。

## 4. 硬冲突（H）— 按字面实现会出错或失控

### H1 增量去重会把 FAILED 记录当成「已下载」，导致失败媒体永不重试

- **位置**：数据库结构说明 §3.1（`status` 含 FAILED）+ §6「增量判断」；需求 F5/F6；时序图 §4.1-d
- **矛盾**：去重查询 `WHERE tweet_id=? AND media_url=?` **不看状态**；而下载失败也会写一条 FAILED 记录（时序图 §6-e）。于是第二次开增量跑同一用户时，上轮失败项命中记录 → 计入 skip → **永远不再尝试**。
- **后果**：F6「失败媒体自动重试」「断点续传」在增量模式下形同虚设；用户看到的是「跳过 N 个」，实际是静默丢件。
- **建议改法**（择一，推荐 a）：
  - a) 去重只认成功：`WHERE tweet_id=? AND media_url=? AND status='SUCCESS'`，FAILED 记录用 `INSERT ... ON CONFLICT(tweet_id,media_url) DO UPDATE` 覆盖重试结果；
  - b) 显式区分「已下载」与「已尝试」，新增 `attempt_count` + `last_attempt_at` 列，重试按次数上限控制。
- **附带**：需同时定义「文件被用户手工删除但记录仍在」的处理——见 S4。

### H2 真实约束是「账号级每日调用配额」，而文档只设计了「频率限流 + 退避」

- **位置**：需求 F16、§1.3 成功标准、§8 验收第 3 条；时序图 §7（429 → 标记冷却 → 换号 → 退避）；详细设计 §4.4
- **矛盾**：X 的限制是**每日调用总量**（原项目 README：「Rate limit exceeded = 该账号当日调用次数已耗尽」，含转推时约 `总推数 / 19`）。配额耗尽后，**退避、延长间隔、并发降为 1 都无效**，只有「换号」或「次日再跑」两条路。
- **后果**：验收第 3 条「触发 Rate Limit 时自动切换账号或退避，程序不直接崩溃」在只有单账号时无法满足；多账号也会被一口气耗光（无预算概念）。
- **建议改法**：
  - 在配置与设计里引入**配额模型**：`quota.per-account-daily`、`quota.reserve-for-retry`，运行前按「目标推文数 ÷ 19」估算所需调用数，不足则拒绝启动并提示需要几个账号；
  - `task_run.api_call_count` 升级为**配额账本**（按账号、按自然日累计，落库或落本地 JSON），跨进程可续；
  - 新增 `QuotaExhaustedException`，与 `RateLimitException` 分开；配额耗尽即**优雅停机并记录续跑点**（配合 S5 水位线），而不是无限退避；
  - 把「下载不计配额」写进非功能需求与日志提示（避免用户以为限流会挡住下载）。

### H3 SQLite 单文件 + 8 并发下载线程直接写库，必然遇到 SQLITE_BUSY

- **位置**：详细设计 §4.6（`MediaDownloader` 线程池并发 + 更新 Storage）、§4.7；数据库结构说明全篇
- **问题**：文档只提到「SQLite + JDBC」，没有 WAL、没有 `busy_timeout`、没有写串行化。默认 journal 模式下并发写会抛 `SQLITE_BUSY`/`database is locked`，而 §4.6 明确「单条失败不阻断整批」——写库失败会被误当成下载失败，污染 FAILED 记录。
- **建议改法**：连接串 `?journal_mode=WAL&busy_timeout=5000&synchronous=NORMAL`；写入走**单写线程 + 有界队列**（下载线程只投递结果），或 `synchronized` 单连接写；失败重试后仍失败需落日志而不是 `save(FAILED)`。

### H4 第一阶段范围三处口径冲突

- **位置**：需求 §6.1（第一阶段含 **F13 多账号池自动轮换**、**F15 代理**）↔ 详细设计 §9（第一阶段「Account（单账号）」，多账号池与代理在第二阶段）↔ index.html（Phase 1 = 单账号）
- **后果**：评审/外包/自己隔两周回来看，都不知道 MVP 到底含不含多账号。而 H2 说明**单账号 MVP 大概率连一个中等用户的媒体时间线都跑不完**（配额），所以这个口径直接决定 MVP 能不能用。
- **建议**：以「配额现实」为准重排——把**多账号池提到第一阶段**（它是可用性的前提，不是增强），代理池可留第二阶段（单代理足够）；三处文档同步改，index.html 一起改。

### H5 `screen_name` 做关联键 + `media_url` 做唯一键，两个键都不稳定

- **位置**：数据库 §3.2（`user_profile.screen_name UNIQUE`，与 `download_record.user_screen_name` 逻辑关联）、§3.1（`UNIQUE(tweet_id, media_url)`）、需求 F4（默认目录以用户名分层）
- **问题**：
  - X 允许改用户名 ⇒ 改名后同一人变成两条主页记录、历史下载记录关联断裂、目录分裂；**应从 `UserByScreenName` 取 `rest_id` 作为稳定主键**（`rest_id` 文档里已有字段却只当普通列）。
  - `media_url` 对图片通常稳定，但视频存在多码率/转码变体，同一媒体可能因 URL 变化重复下载；建议增加 **`media_key`**（X `media_key` 是媒体稳定标识）或 `md5(media_url)` 摘要列作为去重辅助键（原项目正是用 `md5(media_url)[:4]` 规避该问题）。
- **建议**：`user_profile` 主键语义改为 `rest_id UNIQUE`，`screen_name` 降为普通列（`download_record` 加 `user_rest_id`）；`download_record` 增 `media_key TEXT`，唯一键评估改为 `UNIQUE(tweet_id, media_key)` 或保留原键但**同时**落 `media_key` 供后续迁移。

### H6 「喜欢(Likes) 仅限本人账号」与「多账号 Cookie 池自动轮换」语义冲突

- **位置**：需求 F2（Likes 仅限本人账号）vs F13（多账号池自动轮换）
- **问题**：Likes 时间线只能查**该 Cookie 所属账号自身**的喜欢列表。若 AccountPool 轮换，用 A 账号的 Cookie 去拉「elonmusk 的 likes」要么无意义、要么直接 401/403。文档没有任何「任务绑定账号」的概念。
- **建议**：任务模型增加可选的 **`accountBinding`**（`AUTO` / `指定账号名`）；`Likes` 与「仅亮点」默认必须绑定具体账号；`AccountPool.acquire()` 增加 `acquire(String preferred)` 重载；配置里 `accounts[].note` 提示「likes 任务请用本人账号」。

## 8. 外部与合规风险

1. **平台条款与封号**：非官方 GraphQL + Cookie 访问本身即违反 X ToS；Cookie 建议明确「仅用测试小号，禁止主账号」（原项目 README 有该提示，Java 版文档中**缺失**，建议补进需求 §5.2 与操作台提示）。
2. **著作权**：下载内容的著作权归原作者/平台。原项目免责声明含「不得侵权传播」，Java 版文档只写了「不收集、不上传」，建议整段照抄，并落到三处：文档、`--help` 输出、输出目录自动生成的 `README.txt`。
3. **第三方逆向依赖**：TxId 生成算法依赖社区实现，随时可能失效（作者自述概率性失效）⇒ 文档里应把「算法可插拔」升级为「**有明确的失效降级路径**」（S13）。
4. **网络可达性**：文档只写「运行环境网络允许访问 x.com」，应补「中国大陆需合规代理，代理配置非可选」的现实说明。
5. **无官方支持**：接口/字段/queryId 变更无通知渠道 ⇒ 需要 S5+S10 的快速恢复能力，否则工具会在某天毫无预兆地整体失效。
