## 本轮发现并修掉的 Bug（含我自己的操作坑）

1. **SearchTimeline 必须 POST**：同一 qid 用 GET 一律返回**空响应体 404**，改 POST + JSON body 后 200。
   这是 Tag 任务此前完全不通的根因（不是 qid 过期，也不是 TxId）。已在 `operations.yaml` 加 `method: get|post`。
2. **qid 生成脚本把 base-url 抽成 `https://twitter.com/i/api`**：与 path 里的 `/i/api/graphql/...` 叠成双份 → 全部操作 404。
3. **新版 UserByScreenName 没有 `legacy`**：字段搬到 `core.name` / `avatar.image_url` / `banner.image_url` /
   `profile_bio.description` / `tweet_counts.media_tweets`。换新 qid 后曾**静默退化**成「昵称=用户名、推文数=0、媒体数=0」，
   真机跑控制台时才暴露 → 已双 schema 兼容 + 新增 `UserApiTest`（5 个用例）守护。
4. **新版 banner 地址无扩展名**（`…/profile_banners/<id>/<ts>`）：需补 `/1500x500` 才拿得到图，否则落地文件后缀是时间戳。
5. **搜索结果的作者名取不到**：新响应把 screen_name 放在 `core.screen_name`（旧版在 `legacy.screen_name`）→ 曾显示空作者。
6. **dry-run 仍写一行 `task_run`**（`verify-r4.sh` 抓到）：dry-run 现在真正零状态（配额账本照记，因为确实消耗了调用）。
7. **CRLF 让 queryId 回写全部失配**：Windows 编辑器/patch 工具会把文件改成 CRLF，按行比较全部找不到块 → 读入即统一行尾。
8. **日志 appender 占住 JUnit 临时目录**：`loadConfig()` 挂文件 appender 后 `@TempDir` 清理失败（3 个用例报错）→
   改为幂等 + 测试经 surefire 关掉文件日志。
9. **rolling policy 顺序错**：`policy.start()` 前未挂 parent → `rawFileProperty()` 抛错，日志文件一直没生成。
10. **我自己的两个操作坑**（都吃过一次，已写进 README/记录）：
    - **拿旧 jar 联调**（`mvn test` 不更新 jar；`clean` 被运行中的操作台进程锁住 → 构建静默失败，我一度误判"解析只出 1 条"）；
    - **Windows 上 Python 裸调 `bash` 命中 WSL**（必须用 `C:\Program Files\Git\usr\bin\bash.exe`），让构建看起来"跑了但没跑"。

## 关键实测结论

- **TxId（F14）目前不必实现**：`UserMedia` / `SearchTimeline` / `TweetDetail` / `UserTweets` 不带 `x-client-transaction-id`
  均返回 200（配置里已标 `txid`，代码留了 provider 接口）。若将来被收紧，症状是 403 + 空响应体。
- **queryId 会轮换**：原 Python 仓库里的两个 SearchTimeline qid 都已失效；正确做法是
  **从 X 经典客户端 `main.<hash>.js` 现查**（用账号 Cookie 取 `x.com/home` → 解析 `queryId:"…",operationName:"…"` 表），
  已做成 `refresh-operations` 命令，改前自动备份 `operations.yaml.bak-<时间>`。
- **发帖时间与媒体计数在搜索/评论区响应里同样是新版形状**，`TimelineParser` 已对三种作者字段落点做兜底。
